# 面试销售话术与答辩准备

这份文档把 NewsAgent 当成一个要卖给面试官的产品来准备。面试不是“解释代码”，而是让面试官相信：你发现了问题、设计了产品、实现了闭环，并且知道下一步怎么迭代。

---

## 30 秒销售话术（给 HR / 非技术面试官）

> 我做了一个 AI 新闻早报 Agent。它可以每天自动抓取多个新闻源，把重复内容去掉，用大模型分类和摘要，最终生成一份结构清晰的日报，并自动发到邮箱。它解决的是信息过载问题：别人每天花一小时刷新闻，这个产品每天自动给你一份 10 分钟就能读完的简报。整个流程不需要人工值守，所以它已经是一个从抓取到触达用户的完整闭环。

---

## 60 秒技术销售话术（给技术面试官）

> 这个项目用 LangGraph 编排完整工作流，每个阶段都是一个独立节点：异步抓取 RSS、标题去重、HTML 清洗、LLM 批量分类、单篇摘要、分类综述、Markdown 日报、SMTP 邮件推送。入口处有意图识别分流，可以区分“今日简报”和“特定主题检索”。项目还提供 FastAPI 服务、Web 控制台、SQLite 任务历史、Langfuse 可选追踪，以及邮件发送前的人工确认机制。为了控制成本，分类、摘要和分类综述都做了本地缓存，相同内容不会重复调用大模型。

---

## 产品一句话

**NewsAgent = 自动获取信息 + AI 整理信息 + 按时触达用户。**

## 用户是谁

- 需要每天跟踪行业动态的产品经理、运营、投资研究者
- 希望减少信息筛选时间的开发者
- 需要一个内部新闻监测工具的团队

## 产品卖点

1. **省时间：** 多源信息自动合并成一份结构化日报
2. **省成本：** 缓存避免重复调用 LLM
3. **可运行：** 本地、定时任务、CI 都可以跑
4. **可扩展：** 每个节点是独立模块，可以替换数据源、模型、推送渠道

## 面试演示流程

### 第一步：展示产品输出

让面试官先看结果，而不是先看代码。

```bash
python main/demo_product.py
```

打开：

- `examples/demo_report.md`

解释：这就是产品最终交付物。它有分类、摘要、来源、编辑推荐，也有数据口径。

### 第二步：展示真实工作流

有 API Key 和邮箱配置时：

```bash
python main/run_graph.py
```

没有环境时，就讲清楚工作流：

```text
RSS 异步抓取 -> 去重 -> 清洗 -> 分类 -> 摘要 -> 综述 -> 日报 -> 邮件
```

### 第三步：展示工程能力

```bash
pytest tests/
```

重点讲：

- 测试覆盖配置解析、环境依赖、文本清洗、去重、演示输出
- 日志文件方便定位失败环节
- `.env` 与 `.env.example` 分离，密钥不进入仓库
- GitHub Actions 支持定时运行
- FastAPI 提供 `/health`、`/api/agent/run`、`/api/tasks` 等标准化接口
- SQLite 保存任务 ID、用户输入、模型输出、耗时和状态
- Langfuse 可选记录完整 trace
- 邮件发送前支持 Y/N 人工确认

## 常见追问

### 1. 为什么用 LangGraph，而不是普通 Python 流程？

回答方向：

普通流程适合线性脚本，但新闻 Agent 会面临条件分支、状态传递、中间环节失败、后续扩展多源和多推送渠道等问题。LangGraph 把流程变成有向图，节点职责清晰，状态显式传递，还支持 checkpoint、条件路由和可视化，后续更容易扩展成真正复杂的 Agent。

### 2. 大模型成本怎么控制？

回答方向：

三处控制：

- 每个源限制抓取文章数量
- 分类、摘要、分类综述都做本地缓存
- 失败时降级为默认分类或标题摘要，不阻塞整条流程

### 3. 如果某个 RSS 挂了怎么办？

回答方向：

单个源失败不会影响整个工作流。异步抓取时每个源独立处理，网络错误会记录日志并返回空列表；后续节点继续处理其他成功来源。

### 4. 如果分类数量超过阈值怎么办？

回答方向：

工作流里有条件路由。分类后的文章数量超过 20 篇时会进入额外校验节点，再进入摘要阶段。这是为了处理高并发、多来源时内容暴涨的情况。

### 5. 这个项目还有什么不足？

回答方向：

诚实承认比硬吹更重要。

- 当前缓存使用 JSON 文件，适合个人项目，大量数据时应换 SQLite 或数据库
- 当前主要支持 RSS，后续可以接更多平台
- 当前没有 Web 看板，后续可以用 Streamlit 或 FastAPI 提供历史日报、手动触发、导出
- 当前推送只支持 SMTP，后续可以接钉钉、飞书、企业微信、Slack

### 6. 下一步你会怎么做？

回答方向：

优先补一个 Web 看板，因为它是“从脚本变成产品”最关键的一步：用户可以查看历史日报、手动触发任务、看到成本和运行状态。之后再做多平台推送和用户反馈闭环。

## 面试时不要只说“我写了什么”

要说“我为什么做、为谁做、做到什么程度、下一步做什么”。

推荐表达：

- 我不是只做了一个抓取脚本，而是做了一个从信息获取到用户触达的闭环。
- 我做产品时会先确认最终输出：用户每天到底看到什么。
- 我控制成本不是靠省代码，而是靠缓存和失败降级。
- 我知道当前项目边界在哪，也知道下一步优先做什么。

这套表达方式比堆叠技术名词更能让 HR 和面试官记住你的价值。
